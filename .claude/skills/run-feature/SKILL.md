# 파이프라인 실행: $feature ($mode 모드)

너는 이 파이프라인의 **메인 세션(오케스트레이터)**이다. 구현, 테스트, 리뷰를 직접 하지 않는다. 서브에이전트에게 일을 맡기고, 보고를 읽고, 다음에 누구에게 무엇을 맡길지 판단한다. 서브에이전트에게 보내는 지시의 내용과 형식은 네가 판단한다.

- 기능 설계서: `docs/features/$feature.md`
- 고정 계약과 명령: `CLAUDE.md`

## 0. 실행 위치 확인

시작하기 전에 Bash로 `test -d research/tools && echo RESEARCH_REPO || echo RUN_WORKTREE`를 실행한다. 결과가 `RESEARCH_REPO`이면 여기는 실험용 worktree가 아니라 연구 저장소다. 아무것도 하지 말고 "실험용 worktree에서 다시 시작해야 합니다"라고 알린 뒤 끝낸다.

## 서브에이전트

| 이름 | 하는 일 | 파일 수정 |
|---|---|---|
| implementer | `src/` 구현과 수정 | O |
| test-writer | `tests/` 작성과 수정 | O |
| tester | 테스트 실행, 실패 원인 분류 | X |
| reviewer | 코드 리뷰 | X |
| qa | 서버를 띄워 수용 기준 검증 | X |
| security | 보안 점검 | X |
| doc-keeper | 서비스 문서, CHANGELOG, 기능 커밋 | O |

## 진행 규칙

- 서브에이전트끼리는 직접 대화하지 않는다. 모든 전달은 너를 거친다.
- 서브에이전트는 결과를 기다리는 방식(foreground)으로 호출한다. 병렬 단계는 한 메시지에서 여러 에이전트를 동시에 호출한다.
- 같은 에이전트에게 다시 일을 맡길 때는 새로 띄우지 않고, 처음 호출에서 받은 에이전트 id로 **이어서 호출**(SendMessage)한다.
- 1단계 스켈레톤을 빼고는 `src/`와 `tests/`를 직접 고치지 않는다.

## 형상 관리

- 이 실행은 전용 브랜치에서 진행한다. 브랜치를 바꾸거나 다른 브랜치를 병합하지 않는다. `git push`는 하지 않는다.
- 아래 절차에서 **[체크포인트]** 표시가 있는 시점마다 네가 직접 체크포인트 커밋을 만든다.
  - 명령: `git add -A --sparse && git commit -m "wip($feature): <단계 번호> <무엇을 했는지>"`
  - 이 작업 폴더는 일부 파일만 꺼낸 sparse 상태라서 `--sparse`가 없으면 `git add`가 실패할 수 있다.
  - 예: `wip($feature): 3 테스트 루프 2회차 수정`
  - 바뀐 파일이 없으면 커밋하지 않는다.
- 커밋 해시를 기억해 두었다가, 리뷰 2라운드부터 reviewer, qa, security에게 "직전 리뷰 체크포인트" 해시를 알려 준다. 그러면 그 이후 변경분만 확인할 수 있다.
- 기능의 마지막 커밋은 doc-keeper가 만든다. 메시지 첫 줄은 `$feature: <한 줄 요약>`이다.

## 절차

### 1. 계획, 스켈레톤, 화면 목업

- 설계서를 읽고 `docs/plans/$feature-plan.md`를 쓴다. 구현 범위, 모듈 구조, 인터페이스, 화면 목록, 수용 기준과 테스트의 대응을 담는다.
- 새로 만들 모듈의 함수와 클래스를 시그니처와 docstring만 있는 스텁(`raise NotImplementedError`)으로 `src/`에 만든다. 고정 계약 파일은 확장만 한다.
- 설계서에 나온 화면마다 **목업**을 만든다.
  - 위치: `docs/plans/mockups/$feature-<화면 이름>.html`, 그리고 모든 목업으로 가는 링크를 모은 `docs/plans/mockups/$feature-index.html`
  - 브라우저에서 파일을 바로 열어 볼 수 있게 만든다. CSS는 파일 안에 넣고, 외부 파일이나 인터넷 자원을 쓰지 않는다.
  - 실제 화면처럼 예시 데이터(예시 URL, 단축 URL, 오류 문구)를 넣는다. 문구, 배치, 색을 실제 구현이 따라야 할 기준으로 정한다.
- **[H1]** 모드별 처리 (아래 표). 사람에게 보여 줄 때는 계획 요약과 함께 목업 파일 경로를 알려 주고, 브라우저로 `$feature-index.html`을 열어 확인해 달라고 요청한다.
- **[체크포인트]** `1 계획, 스켈레톤, 목업`

### 2. 구현과 테스트 작성 (병렬)

- implementer와 test-writer를 동시에 호출한다. 화면이 있는 기능이면 목업 경로도 함께 알려 준다.
- **[체크포인트]** `2 구현과 테스트 작성`

### 3. 테스트 루프 (최대 5회)

1. tester를 호출한다.
2. 결과가 PASS면 4단계로 간다.
3. FAIL이면 실패 항목을 분류별로 넘긴다.
   - code_bug → implementer
   - test_bug → test-writer
   - spec_ambiguous → **[H2]**
4. 수정이 끝나면 **[체크포인트]** `3 테스트 루프 <n>회차 수정`을 만들고 tester를 이어서 호출한다.
5. 5회를 넘으면 **[한도 초과]** 처리.

### 4. 리뷰 루프 (최대 5라운드)

1. 검토할 상태가 모두 커밋되어 있는지 확인한다. 이 커밋이 이번 라운드의 리뷰 체크포인트다.
2. reviewer, qa, security를 동시에 호출한다. 2라운드부터는 이어서 호출하고, 이전 지적의 해결 여부와 직전 리뷰 체크포인트 이후 변경분만 확인하게 한다.
3. 세 보고의 지적을 모아 중복을 합친다.
   - blocker와 major가 0건이면 루프를 끝내고 5단계로 간다.
   - minor는 고치지 않고 기록만 한다.
   - 같은 지적이 2라운드 연속 해결되지 않으면 "미해결"로 표시하고 이후 라운드에서 뺀다.
4. 1라운드가 끝난 뒤에는 **[H3]** 모드별 처리.
5. blocker와 major 목록을 implementer에게 넘겨 수정하게 한다.
6. tester를 다시 호출한다. 실패하면 3단계 규칙을 따른다.
7. **[체크포인트]** `4 리뷰 <r>라운드 수정`
8. 5라운드가 끝나도 남은 지적은 "미해결"로 기록하고 5단계로 간다.

### 5. 커밋 전 확인

**[H4]** 모드별 처리.

### 6. 실행 보고서

`docs/plans/$feature-report.md`를 쓴다. 담을 내용:

- 단계별 진행 기록과 각 단계에서 호출한 에이전트, 체크포인트 커밋 목록
- 테스트 루프 횟수, 리뷰 라운드 수, 라운드별 지적 수(심각도별)
- 미해결 지적과 minor 지적 목록
- 설계서 해석 결정 목록
- 종료 상태: 완료 또는 실패와 그 이유

### 7. 문서와 기능 커밋

doc-keeper를 호출한다. doc-keeper는 서비스 문서와 CHANGELOG를 갱신하고, 남은 변경(실행 보고서 포함)을 모두 담아 기능 커밋 하나를 만든다.

## 모드별 사람 개입

| 지점 | auto | human | default |
|---|---|---|---|
| H1 계획·목업 승인 | 스스로 승인하고 진행 | 사람에게 계획과 목업을 보여주고 승인이나 수정 요청을 기다림. 수정 요청이 오면 반영한 뒤 다시 확인받음 | human과 같음 |
| H2 설계서 모호함 | 네가 해석을 정하고 `docs/plans/$feature-decisions.md`에 기록 | 사람에게 질문하고 답을 기다림 | auto와 같음 |
| H3 리뷰 1라운드 후 | 네가 우선순위를 정함 | 사람에게 지적 목록을 보여주고 우선순위와 제외할 항목을 받음 | auto와 같음 |
| H4 커밋 전 | 바로 진행 | 사람에게 결과를 보여주고 확인을 기다림 | auto와 같음 |
| 한도 초과 | 실패로 기록하고 6단계로 감 | 사람에게 넘김 | human과 같음 |

auto 모드에서는 사람에게 묻지 않는다. 판단이 필요하면 스스로 정하고 근거를 기록한다.
