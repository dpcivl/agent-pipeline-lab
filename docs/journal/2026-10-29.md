## 결정

| 결정 | 이유 |
|---|---|
| 테스트 실패는 tester가 아니라 implementer가 수정 | 판정자가 수정까지 하면 테스트를 고쳐 통과시키는 왜곡이 가능하고, 측정할 에이전트 간 피드백 경로가 사라짐 |
| 실패 원인을 코드 버그·테스트 오류·설계서 모호함으로 분류 | 테스트 작성 에이전트가 설계서를 잘못 읽은 경우를 구분하기 위해 |
| 테스트 루프·리뷰 루프 모두 최대 5회 | 사람 개입을 최소화하는 것이 목표 |
| 사람 개입은 설계서 작성과 계획 승인만 | 위와 같음 |
| 모델 배정: 메인·reviewer·security는 Opus 5.5, implementer·test-writer·tester·qa는 Sonnet 5.5, doc-keeper는 Haiku 5.5 | 판단 정확도가 루프 횟수를 좌우하는 곳에 상위 모델을 씀 |
| 자율 모드와 개입 모드 비교 실험 추가 | 사람 개입이 품질과 토큰에 주는 영향을 측정하기 위해 |
| 원본 트랜스크립트는 공개하지 않음 | 로컬 경로와 계정 정보가 들어 있음 |
| 에이전트 간 소통 분석을 연구의 핵심 축으로 추가 | 가장 알고 싶은 것이 에이전트끼리 주고받는 프롬프트의 내용과 소통 과정, 그리고 사람이 얻을 수 있는 프롬프팅 교훈이기 때문 |
| 메인의 지시 프롬프트는 자유, 서브에이전트의 보고는 형식 고정 | 지시 양식을 정하면 LLM의 자연스러운 지시 방식을 관찰할 수 없음. 보고는 다음 단계 판단에 필요 |
