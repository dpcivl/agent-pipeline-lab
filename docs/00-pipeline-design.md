## 0. 연구 질문 (재정리)

1. 메인 세션 ↔ 서브에이전트 사이에 오가는 **raw 프롬프트의 형식**은 무엇인가?
2. 에이전트 간 **소통에 쓰이는 토큰**(지시 프롬프트 + 결과 보고)은 얼마인가? 전체 대비 비중은?
3. 기능 하나를 파이프라인으로 끝까지 구현하면 **총 토큰/비용/시간**은 얼마인가? 단계별 분포는?
4. 이 파이프라인이 실제로 **동작하는가** — 사람은 설계서 작성과 계획 승인 2회만 개입하고, 나머지는 에이전트끼리 프롬프트를 주고받으며 기능이 완성되는가?
5. 사람이 개입했을 때와 개입하지 않았을 때 **결과물 품질과 토큰 사용량**은 어떻게 다른가? (5절 비교 실험)
6. 메인이 서브에이전트에게 쓰는 지시 프롬프트는 **어떤 내용과 구조**를 가지며, 보고가 메인을 거쳐 전달될 때 **무엇이 빠지고 더해지는가**? (6절)
7. 에이전트 간 소통에서 사람이 프롬프트를 쓸 때 활용할 수 있는 **효율적인 프롬프팅 패턴**은 무엇인가? (6절)

### 환경 사실 확인 (이 PC 기준, Claude Code 2.1.x)

| 항목 | 확인 내용 |
|---|---|
| 메인 세션 기록 | `~/.claude/projects/<프로젝트slug>/<sessionId>.jsonl` |
| 서브에이전트 기록 | `~/.claude/projects/<slug>/<sessionId>/subagents/agent-<id>.jsonl` + `agent-<id>.meta.json` |
| 부모-자식 연결 | `meta.json`의 `toolUseId` = 부모 jsonl의 `Agent` tool_use 블록 id. 같은 id의 `tool_result`가 서브에이전트의 최종 보고 |
| raw 프롬프트 | 서브에이전트 jsonl의 **첫 user 레코드** `message.content`가 메인이 보낸 프롬프트 원문 그대로 |
| 토큰 | 모든 assistant 레코드에 `message.usage` (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `thinking_tokens`)와 `message.model` |
| 시스템 프롬프트 | 트랜스크립트의 `prompt_snapshot` 첨부에 기록됨 (세팅 중 확인). 원문은 비공개, 크기만 집계 |
| 이어서 호출 | 서브에이전트 트랜스크립트에 머리말이 붙은 `isMeta` user 레코드로 기록됨 |
| 보고 전달 | 데스크톱 앱에서는 `SubagentHandback` 도구 호출로 전달됨 |
| 도구 | uv 0.12.12, git 2.55, Python 3.12.10 |

**중요한 구조적 사실:** Claude Code에서 서브에이전트끼리는 직접 대화하지 않습니다. 모든 통신 경로는 ① 메인 → 서브 (Agent 도구의 `prompt` 문자열 1개), ② 서브 → 메인 (서브의 마지막 assistant 텍스트가 tool_result로 반환), ③ 공유 파일시스템(설계서, 코드, 테스트) 세 가지뿐입니다. 따라서 "에이전트끼리의 소통"을 측정한다는 것은 ①②의 토큰과, 메인 세션이 ②를 읽고 다음 ①을 작성하는 데 쓰는 **오케스트레이션 오버헤드**를 측정하는 것입니다.

## 1. 제안한 파이프라인 검토

원안:
```
설계(사람) → 계획+목업(메인) → 승인(사람)
→ [S1 구현 ∥ S2 테스트작성] → [S3 테스트 ∥ S4 리뷰 ∥ S5 QA ∥ S6 보안] → S7 문서/형상 → 보고서(메인)
```

전체 골격은 좋습니다. 다만 다음 5가지를 보완해야 실제로 돌아갑니다.

| # | 문제 | 보완 |
|---|---|---|
| 1 | **수정 루프 없음.** S3가 테스트 실패를 발견해도 고치는 단계가 없고, S4/S5/S6가 깨진 코드를 동시에 리뷰함 | S3는 **실행·판정만** 하고 실패 원인을 분류해 보고 → 메인이 원인별로 S1(코드)·S2(테스트)에게 전달하고, 설계서 모호함은 메인이 해석을 결정해 기록 → S3 재실행(최대 5회). **green 게이트** 뒤에 S4/S5/S6 실행. 수정 주체를 S3에 두지 않는 이유: 판정자가 수정까지 하면 테스트를 고쳐 통과시키는 왜곡이 가능하고, 측정 대상인 에이전트 간 피드백 엣지가 사라짐 |
| 2 | **S1·S2 병렬의 인터페이스 불일치.** 둘 다 설계서만 보면 함수명/모듈 경로/스키마가 어긋나 S3가 맞추느라 토큰을 태움 | 메인의 "목업" 산출물을 **인터페이스 스켈레톤**(시그니처 + docstring + `NotImplementedError` 스텁 파일, 테스트 파일명)으로 정의. 승인 대상에 포함 |
| 3 | **리뷰 결과를 반영하는 단계 없음.** S4/S5/S6의 findings가 보고서에만 남음 | 리뷰 → 수정 → 테스트 → **재리뷰**를 반복하는 루프를 **최대 5라운드**. 심각도 blocker/major가 0건이 되면 종료. 무한 반복을 막기 위해 2라운드부터는 변경분과 이전 findings만 재검토하고, 같은 지적이 2라운드 연속 해결되지 않으면 "미해결"로 기록하고 제외 |
| 4 | **쓰기 충돌.** 서브에이전트는 같은 작업 디렉터리를 공유 | S1은 `src/`만, S2는 `tests/`만 쓰도록 프롬프트와 에이전트 정의에서 제한. S3·S4·S5·S6는 **Edit/Write 도구 없이** 정의(`.claude/agents/*.md`의 `tools:`로 강제). S3·S5는 pytest·서버 실행에 Bash가 필요하므로 파일 수정 금지는 프롬프트로 지시하고, 실행 후 `git status`로 변경이 없었는지 확인. Write/Edit 도구는 `research/hooks/guard_write.py` 훅이 역할별 쓰기 영역 밖이면 차단 |
| 5 | **역할 중복.** 리뷰/QA/보안의 경계가 흐리면 같은 지적을 3번 받음 | 리뷰=정적 코드 품질·정확성, QA=서비스를 실제로 띄워 설계서의 수용 기준을 블랙박스 검증, 보안=OWASP 체크리스트+의존성. 겹침 정도 자체도 연구 결과로 기록 |

### 개선된 파이프라인 (v2)

```
0. 프로젝트 세팅 (최초 1회) ─ uv, git, .claude/agents 7종, hooks, 수집 스크립트, CLAUDE.md
1. 기능 설계서 (사람)            → docs/features/F{n}.md  (요구사항 + 수용 기준)
2. 구현 계획 + 인터페이스 스켈레톤 + **화면 목업** (메인) → docs/plans/F{n}-plan.md + src/tests 스텁 + docs/plans/mockups/ (브라우저로 바로 여는 HTML) (7.2절 고정 계약 안에서 자유 영역 구조 결정)
3. 계획·목업 검토와 승인 (사람)                   ◆ 사람 게이트 1
4. [병렬] implementer (S1, src/)  ∥  test-writer (S2, tests/)
5. 테스트 루프                                              ◆ green 게이트
   5a. tester (S3, 읽기 전용): pytest 실행 → 실패마다 원인 분류해 보고
       - code_bug      : 구현이 설계서/스켈레톤과 다름
       - test_bug      : 테스트가 설계서를 잘못 해석
       - spec_ambiguous: 설계서만으로 판단 불가
   5b. 메인: code_bug → implementer, test_bug → test-writer,
       spec_ambiguous → 메인이 설계서 해석을 결정해 docs/plans/F{n}-decisions.md에 기록 후
       implementer·test-writer 양쪽에 전달 (사람은 최종 보고서에서 사후 확인)
       (implementer·test-writer는 새로 띄우지 않고 SendMessage로 이어서 호출)
   5c. 수정 후 tester 재실행. 최대 5회, 넘으면 파이프라인 중단 후 사람에게 넘김 (유일한 중간 개입 지점)
6~7. 리뷰 반영 루프 (최대 5라운드)                          ◆ 품질 게이트
   6. [병렬, 읽기전용] reviewer (S4) ∥ qa (S5) ∥ security (S6)
      → findings마다 심각도(blocker / major / minor), 위치, 근거, 수정 제안
   7a. 메인: 세 에이전트 findings 중복 제거·취합
       - blocker/major가 0건이면 루프 종료 → 8단계
       - minor는 고치지 않고 보고서에만 기록
   7b. 메인 → implementer (이어서 호출): blocker/major 목록 전달, 수정
   7c. tester 재실행 (5단계 규칙 그대로 적용)
   7d. 다음 라운드: S4/S5/S6를 이어서 호출해 다음 두 가지만 검토
       ① 이전 findings가 해결됐는지  ② 이번 라운드 변경분(git diff)에 새 문제가 있는지
   종료 조건: blocker/major 0건 또는 5라운드 도달
   정체 방지: 같은 finding이 2라운드 연속 해결되지 않으면 "미해결"로 표시하고 이후 라운드에서 제외
   5라운드 후 남은 finding은 사람에게 묻지 않고 보고서의 "미해결" 항목으로 넘김
8. 실행 보고서 (메인): docs/plans/F{n}-report.md
9. doc-keeper (S7): docs/service.md·CHANGELOG.md 갱신, 보고서까지 담아 기능 커밋 하나 (7.5절)
```

에이전트는 `.claude/agents/<name>.md`로 정의합니다(이름, 역할 시스템 프롬프트, 허용 도구, 모델). 이렇게 하면 역할 프롬프트가 레포에 버전 관리되고, 연구 재현이 가능합니다.

### 검토한 대안

- **Workflow 도구(스크립트 기반 결정론적 오케스트레이션)** — 4~8단계를 스크립트로 돌릴 수 있지만, 메인 세션의 오케스트레이션 비용(연구 대상)이 사라집니다. 기준선은 Agent 도구 방식으로 측정하고, 여유가 있으면 F3 이후 비교군으로 돌리는 것을 권합니다.
- **worktree 격리(`isolation: worktree`)** — S1/S2를 별도 worktree에서 돌리면 충돌은 없지만 병합 단계가 추가되어 측정이 복잡해집니다. 경로 분리로 충분하므로 사용하지 않습니다.

### 에이전트별 모델 배정 (v1.4, 확정 2026-10-29)

배정 원칙: **판단의 정확도가 루프 횟수를 좌우하는 곳에는 상위 모델, 기계적인 작업에는 하위 모델.**
리뷰·보안 계열은 코드를 많이 읽고 짧게 쓰는 입력 위주 작업이라 비용 대부분이 cache read에서 나옵니다. Opus 5.5는 Sonnet 5.5보다 cache read를 포함한 모든 단가가 2배이므로, 이 두 역할의 비용도 Sonnet을 쓸 때의 약 2배가 됩니다. 놓친 결함 때문에 루프가 늘어나는 비용이 더 크다고 보고 Opus를 유지합니다.

> v1.9 정정: 이전 버전은 "Opus와 Sonnet의 cache read 단가가 같아 추가 비용이 작다"고 적었으나, 공식 가격표 확인 결과 Sonnet 5.5의 cache read는 $0.10으로 Opus 5.5($0.20)의 절반입니다.

## 2. raw 프롬프트 확인·저장 방법

두 겹으로 수집합니다. A가 정답 소스, B는 레포 안에 실시간으로 남는 보조 로그입니다.

### A. 트랜스크립트 JSONL 수집 (사후, 정확)
기능 하나가 끝나면 `research/tools/collect.py <sessionId>`를 실행:
1. 메인 jsonl에서 `Agent` tool_use(지시 프롬프트)와 짝이 되는 tool_result(보고)를 추출
2. `subagents/*.meta.json`의 `toolUseId`로 서브에이전트 jsonl을 연결
3. 이어서 호출(SendMessage)로 보낸 메시지도 같은 방식으로 추출
4. 실행 폴더의 `messages/`에 메시지 한 개당 파일 하나로 저장 (형식은 6.3절)
5. jsonl 원본은 실행 폴더의 `transcripts/`에 복사(재분석용, 비공개)

### B. Hooks 실시간 로깅 (보조)
`.claude/settings.json`에 프로젝트 hooks를 등록합니다. 내용은 `research/config/claude-settings.json`에 있으며, Claude Code 설정 파일이라 **사람이 직접 설치**합니다.
- `log_agent_event.py`: `UserPromptSubmit`, `PreToolUse`/`PostToolUse`(matcher `Agent|SendMessage`), `SubagentStart`, `SubagentStop`의 입력 전체를 `research/logs/events/`에 이벤트마다 파일 하나로 기록. 병렬 서브에이전트가 한 파일에 동시에 이어 쓰면 줄이 섞이기 때문(검증 중 확인). `PostToolUse`의 Agent `tool_response`에는 usage와 소요 시간이 담김
- `guard_write.py`: `PreToolUse`(matcher `Write|Edit|NotebookEdit`). 서브에이전트가 7.3절 쓰기 영역 밖에 쓰면 차단하고 기록
- `guard_bash.py`: `PreToolUse`(matcher `Bash`). 서브에이전트이거나 실험 worktree(`research/tools/`가 없는 sparse worktree)이면 `git push`를 차단하고 기록. 연구 세션은 push 가능
- 같은 파일의 `permissions`에 테스트·린트·git 조회 명령을 허용. `git push` 금지는 deny 규칙이 아니라 위 hook으로 처리 (deny 규칙은 연구 세션의 push까지 막기 때문)

### C. 한계 (연구 보고서에 명시)
- 서브에이전트의 **시스템 프롬프트**는 트랜스크립트의 `prompt_snapshot` 첨부에 기록됩니다 (세팅 중 확인, Claude Code 2.1.308). Claude Code 내장 프롬프트가 포함되고 세션 정보가 섞인 첨부도 있으므로 원문은 공개하지 않고, `collect.py`가 크기(글자 수)만 `agents.csv`에 남깁니다. 고정 오버헤드 토큰은 역할별 빈 작업 실행으로 따로 측정합니다.
- CLAUDE.md는 모든 서브에이전트에 주입되므로 **짧게** 유지해야 합니다(토큰 비용 변수).
- 쓰기 영역 hook(`guard_write.py`)은 Write/Edit 도구만 검사합니다. Bash의 리다이렉션이나 heredoc으로 쓰는 경우는 막지 못하므로, 실행 후 `git diff`로 에이전트별 변경 파일을 사후 확인합니다.
- 데스크톱 앱의 auto 권한 모드는 서브에이전트에게도 "파일 작업은 가능하면 Bash로 하라"는 지침을 주입합니다(검증 중 확인). 이 모드로 실험하면 쓰기 영역 hook을 우회하는 쓰기가 늘고, 도구 사용 패턴도 달라집니다. 실험 권한 모드는 **auto 모드로 확정**했습니다(2026-10-29). 이 지침은 모든 실행에 똑같이 들어가므로 모드 간 비교에는 영향이 없고, 실험 조건으로 기록합니다. 권한 확인 건너뛰기 모드는 사용자 계정 권한으로 확인 없이 명령을 실행해 격리되지 않은 이 컴퓨터에서는 쓰지 않습니다.

## 3. 토큰 추적 설계

### 측정 단위
| 수준 | 지표 |
|---|---|
| 에이전트 1회 실행 | API 호출 수, input / output / cache_write / cache_read / thinking 토큰, 모델, 추정 비용, 시작~종료 시각, 도구 호출 수 |
| 통신 엣지 (메인→서브, 서브→메인) | 지시 프롬프트 토큰, 보고 토큰 (Anthropic `count_tokens` API로 정확히 계산, 키 없으면 문자수 기반 추정으로 표기) |
| 메인 세션 | 세션 전체 usage. **기능 1개 = 메인 세션 1개**로 운영해 귀속 문제를 없앰 |
| 기능 전체 | 메인 + 모든 서브에이전트 합계, 단계별(4·5·6·7·8) 분포, 통신 토큰 비중, 고정 오버헤드 비중 |

### 비용 계산
- 모델별 단가표를 `research/config/pricing.json`에 두고(세팅 시 최신 단가 확인), cache_read·cache_write 가중치를 적용해 "청구 기준 비용"과 "원시 토큰 합계"를 둘 다 보고합니다. cache_read는 호출마다 누적되므로 원시 합계가 매우 크게 보이는 점을 보고서에 설명합니다.

### 교차 검증
- `ccusage`(npm) 같은 외부 jsonl 파서로 합계를 교차 확인합니다. OpenTelemetry 내보내기는 범위에서 제외(연구에 과함).

### 고정 오버헤드 측정 (P2)

에이전트를 일 없이 호출해 호출 한 번의 고정 토큰을 잽니다. 실험과 같은 조건이어야 하므로 `new_run.py P2 auto <반복>`으로 만든 worktree의 새 세션(auto 모드, 메인 Opus 5.5)에서 `/measure-baseline`을 실행합니다.

- 1차(콜드): 7종을 같은 문구의 빈 지시로 동시에 호출
- 2차(웜): 같은 7종을 새로 띄워 한 번 더 호출. 1차가 만든 캐시를 얼마나 재사용하는지 봄
- 지표: 에이전트별 첫 API 호출의 input, cache write, cache read 토큰과 비용, 시스템 프롬프트 크기
- 반복: 2회 (`r1`, `r2`)

### 수정 루프 측정 항목
- 루프 횟수, 실패 원인 분류별 건수(code_bug / test_bug / spec_ambiguous)
- 루프 1회당 토큰: tester 보고 → 메인 라우팅 → 수정 에이전트 → tester 재실행 합계
- **이어서 호출 vs 새로 호출**: 본 실험은 모두 이어서 호출(SendMessage)로 고정합니다. 새로 호출하는 방식과의 비교는 6.6절과 함께 선택 실험으로 둡니다.

### 리뷰 루프 측정 항목
- 종료까지 걸린 라운드 수, 종료 사유(blocker/major 0건 / 5라운드 도달)
- 라운드별 findings 수(심각도별, 에이전트별) → **수렴 곡선**: 라운드가 지날수록 줄어드는가, 새 지적이 계속 나오는가
- 라운드별 토큰: 리뷰 3종 + 메인 취합 + 수정 + 재테스트 합계. 1라운드(전체 검토) 대비 2라운드 이후(변경분 검토) 비용 비율
- 에이전트 간 중복 지적 비율, 미해결로 넘어간 finding 수

### 측정 프로토콜
1. **실행마다 새 메인 세션**에서 시작, 세션 id를 `research/runs/F{n}/{mode}/r{k}/session.txt`에 기록 (worktree마다 ~/.claude/projects 아래 폴더가 달라지므로 collect.py는 세션 id로 전체 프로젝트 폴더를 검색)
2. 에이전트별 모델 배정을 3개 기능에 걸쳐 **고정** (1절 "에이전트별 모델 배정")
3. 기능 종료 후 `collect.py` 실행 → `usage.csv`, `edges.csv`, `summary.md` 생성
4. 3개 기능 비교표 → `research/REPORT.md`

## 4. 대상 서비스: **ShortLink — URL 단축 웹 서비스**

스택: Python 3.12 + uv, FastAPI, Jinja2 템플릿(서버에서 HTML 생성), SQLite(표준 `sqlite3`), pytest + httpx2. 별도 프론트엔드 프레임워크와 빌드 도구는 쓰지 않습니다.

> v1.16 변경: 처음에는 API만 만드는 서비스였으나, 연구자의 관심이 "웹·앱 개발 프로젝트에 에이전트 파이프라인을 적용할 수 있는가"이므로 웹 화면을 추가했습니다. 서버 렌더링을 고른 이유는 언어 하나, 빌드 도구 없이 웹 화면을 만들 수 있어 실행 간 편차와 비용을 줄일 수 있기 때문입니다. React 같은 프론트엔드 프레임워크는 이후 비교 대상으로 남깁니다.

선택 이유: 도메인이 널리 알려져 있어 에이전트가 도메인 이해에 토큰을 쓰지 않고(파이프라인 오버헤드만 분리 측정), 기능마다 수용 기준이 명확하며, F2·F3가 F1 코드를 **수정**하므로 신규 작성뿐 아니라 변경 작업의 비용도 측정됩니다. 입력 검증·인증·만료가 있어 보안/QA 에이전트가 실질적으로 할 일이 있습니다.

| 기능 | 내용 | 규모 | 측정 포인트 |
|---|---|---|---|
| **F1 단축·리다이렉트** | 웹 화면(홈, 결과, 입력 오류, 찾을 수 없음)과 API `POST /links`; `GET /{code}` → 302. http/https만 허용, 코드 충돌 처리, SQLite 저장 | 소 | 그린필드 기준선, 목업 확인 단계 |
| **F2 통계·커스텀 별칭** | 클릭 카운트와 통계 화면·API, 생성 화면과 API에 `alias` 옵션(유일성·예약어 검사) | 중 | 기존 코드와 화면 수정 비용 |
| **F3 인증·만료·삭제** | API 키 인증, 만료(만료 시 410), 삭제, 단순 rate limit, 키를 입력해 내 링크를 관리하는 화면 | 대 | 보안 에이전트 findings, 수정 루프 비용 |

## 5. 비교 실험: 사람 개입 vs 자율

목적: 사람이 개입했을 때와 개입하지 않았을 때 **결과물 품질**과 **토큰 사용량**이 어떻게 달라지는지 측정합니다.
방법: 같은 기능을 "자율 모드"와 "개입 모드"로 각각 실행하고, 에이전트가 볼 수 없는 평가 테스트로 똑같이 채점합니다.

### 5.1 두 모드 정의

두 모드 모두 사람이 쓴 **같은 설계서**(docs/features/F{n}.md)로 시작합니다. 설계서는 입력이므로 개입으로 세지 않습니다.

| 시점 | 자율 모드 (auto) | 개입 모드 (human) |
|---|---|---|
| H1 계획·스켈레톤 | 메인이 자동 승인 | 사람이 검토, 수정 요청 가능 |
| H2 설계서 모호함 (spec_ambiguous) | 메인이 해석을 정하고 decisions.md에 기록 | 사람에게 질문 |
| H3 리뷰 1라운드 후 | 메인이 우선순위 결정 | 사람이 우선순위 지정, 불필요한 지적 제외 |
| H4 커밋 직전 | 바로 커밋 | 사람이 최종 확인, 수정 요청 가능 |
| 루프 한도 초과 | 실패로 기록하고 종료 | 사람에게 넘김 |

- 개입 시점은 H1~H4로 **고정**합니다. 그 외 시점에는 개입하지 않아야 반복 실행의 조건이 같아집니다.
- `human-log.md`는 `collect.py`가 트랜스크립트에서 자동 생성합니다. 사람 메시지마다 시각, 메인의 직전 응답부터 걸린 시간, 글자 수를 적습니다. 연구자는 H1~H4 구분과 결정 내용을 메모로 덧붙입니다.
- 1절의 기본 파이프라인(계획 승인 1회)은 두 모드의 중간입니다. 예산이 허락하면 세 번째 모드로 추가합니다.
- 모드 전환은 메인 세션 시작 명령으로 합니다 (예: `/run-feature F1 auto`). 모드별 규칙은 이 명령의 지침 파일에 적어 에이전트 정의와 분리합니다.

### 5.2 통제 조건

| 항목 | 방법 |
|---|---|
| 같은 시작점 | 실행마다 같은 git 태그에서 **별도 worktree**를 만들고 새 메인 세션을 띄움 (`../agent-pipeline-lab-runs/F1-auto-r1/` 등) |
| F2·F3 시작점 | F1이 끝나면 평가 점수가 가장 높은 실행 하나를 `promote.py`로 main에 반영하고 `baseline-F2` 태그를 붙임(7.5절). 두 모드 모두 그 태그에서 F2를 시작 (F3도 같은 방식). 모드별 결과가 누적되며 갈라지는 것을 막음 |
| 같은 설정 | 모델 배정, 에이전트 정의, CLAUDE.md, 루프 한도를 모든 실행에서 동일하게 유지. 실행 시작 시 이 파일들의 해시를 기록 |
| 반복 실행 | LLM 결과는 매번 다르므로 **모드별·기능별 2회**. 기능 3 × 모드 2 × 2회 = **총 12회** |
| 실행 순서 | 자율 모드를 먼저 돌리고 결과를 열어보지 않음. 먼저 보면 개입 모드에서 사람의 판단이 달라지기 때문 |
| 권한 모드 | 모든 실행을 **auto 모드**로 시작. 분류기가 위험한 명령을 확인 창 없이 거절하므로 자율 실행이 끊기지 않음. 분류기 거절 횟수도 기록 |
| 연구 문서 격리 | 실행 worktree는 sparse-checkout으로 연구 문서와 다음 기능 설계서를 제외 (7.4절) |
| 평가 테스트 격리 | 연구 저장소의 `research/eval/`에 보관. 실험 worktree는 sparse checkout으로 이 폴더를 꺼내지 않음. 실행 후 `collect.py`가 트랜스크립트에서 이 경로를 건드린 도구 호출을 찾아 `eval-access.json`에 기록하고, 접근한 실행은 무효 처리 |

### 5.3 결과물 품질 지표

1. **숨긴 평가 테스트 통과율 (핵심 지표)**
   - 기능별 수용 테스트를 실험 전에 따로 만들어 `research/eval/<기능>/`에 둡니다(실험 worktree에는 포함되지 않음). 에이전트는 볼 수 없습니다.
   - 설계서의 수용 기준을 모두 포함하고, 보안 함정 케이스를 넣습니다. 예: `javascript:` URL, 예약어 별칭, API 키 없는 삭제, 만료 링크 접근.
   - 초안은 파이프라인 밖의 별도 Claude 세션이 만들고 **사람이 검토**합니다.
   - 실행 결과 worktree에 평가 테스트를 복사해 돌리는 스크립트로 채점합니다.
   - 평가 테스트는 `create_app`과 `Settings`만 import하고 HTTP 요청으로만 검증합니다 (7.2절). 내부 구조가 달라도 똑같이 채점됩니다.
2. **정적 지표:** ruff 린트 오류 수, 커버리지(%), radon 복잡도, bandit 보안 경고 수.
3. **블라인드 비교 평가:** 어느 모드 결과인지 가리고(A/B 무작위 표기) 두 코드를 나란히 평가합니다. 평가자는 파이프라인에서 쓰지 않는 **Fable 5.1**입니다. 같은 모델이 자기 결과를 높게 보는 편향을 줄이기 위해서입니다. 루브릭: 정확성, 설계서 충실도, 코드 품질, 보안, 테스트 품질 (각 1~5점).
4. **과정 지표:** 테스트 루프·리뷰 루프 횟수, 미해결 finding 수, 실패 종료 여부, 완료까지 걸린 시간.

### 5.4 토큰 지표

| 지표 | 내용 |
|---|---|
| 모드별 총량 | 실행당 총 토큰과 API 환산 비용, 2~9단계별 분포 |
| 개입 유발 토큰 | 사람의 피드백 이후 발생한 재계획·재수정 토큰. human-log.md의 시각과 트랜스크립트 타임스탬프로 구간을 나눠 계산 |
| 품질 대비 비용 | 평가 테스트 1개 통과당 API 환산 비용 |
| 사람 비용 | 개입 횟수, 개입 총 소요 시간(분), 사람이 보낸 메시지 글자 수 |

## 6. 에이전트 간 소통 분석

이 연구의 핵심 축입니다. 에이전트끼리 주고받는 프롬프트의 **내용**을 분석해, 사람이 프롬프트를 쓸 때 활용할 수 있는 인사이트를 얻는 것이 목적입니다.

### 6.1 소통 구조

서브에이전트끼리는 직접 대화하지 않습니다. 모든 메시지는 메인 세션을 거칩니다. tester가 실패를 보고하면, 메인이 그 보고를 읽고 implementer에게 보낼 지시를 **새로 작성**합니다.

```
            ┌──────────── 메인 세션 (허브) ────────────┐
 사람 ──▶  │  보고를 읽고 → 판단 → 다음 지시를 새로 작성  │
            └──┬──────▲──────┬──────▲──────┬──────▲───┘
         지시  │  보고 │  지시 │  보고 │  지시 │  보고 │
               ▼      │      ▼      │      ▼      │
          implementer      tester         reviewer …
               └──────── 공유 파일 (코드·테스트·설계서) ────────┘
```

분석 대상 프롬프트는 세 층입니다.

| 층 | 누가 쓰나 | 변하는가 | 위치 |
|---|---|---|---|
| L1 역할 정의 | 우리 (사람) | 고정 | `.claude/agents/*.md` |
| L2 지시 프롬프트 | 메인 세션 (LLM) | 호출마다 새로 작성 | Agent 호출의 prompt, 이어서 호출할 때의 메시지 |
| L3 보고 | 서브에이전트 (LLM) | 호출마다 | 서브에이전트의 마지막 메시지 |

L2는 **LLM이 LLM에게 쓰는 글**이라 가장 중요한 분석 대상입니다. 공유 파일은 간접적인 소통 수단으로, 메시지가 파일을 가리키는지 내용을 직접 붙여 넣는지를 함께 봅니다.

### 6.2 프롬프트 자유도 (확정 2026-10-29)

| 대상 | 방침 | 이유 |
|---|---|---|
| L2 지시 프롬프트 | **자유** — 형식을 정하지 않음 | 양식을 정하면 LLM이 원래 어떻게 지시를 쓰는지 관찰할 수 없음 |
| L3 보고 | **형식 고정** — 실패 원인 분류, findings 심각도 등 | 메인이 다음 단계를 판단하려면 일정한 형식이 필요 |

오케스트레이션 지침(`/run-feature`)에는 "누구에게 무엇을 맡길지"만 적고 "어떻게 쓸지"는 적지 않습니다.

### 6.3 수집과 정리

실행마다 `research/runs/F{n}/{mode}/r{k}/` 아래에 생성합니다.

| 산출물 | 내용 |
|---|---|
| `messages/NNN-<from>-to-<to>-<type>.md` | 메시지 한 개당 파일 하나. 앞부분에 순번, 보낸 쪽, 받는 쪽, 종류, 라운드, 시각, 토큰, 응답 대상 메시지 번호. 본문은 원문 (비식별화 후) |
| `messages.jsonl` | 위와 같은 내용을 분석용으로 한 줄씩 |
| `flow.md` | 메시지 흐름을 Mermaid 시퀀스 다이어그램으로 자동 생성 |
| `annotations.csv` | 메시지별 코딩 결과 (6.4) |

- 수집 범위: 최초 호출의 지시, **이어서 호출할 때 보낸 메시지(SendMessage)**, 보고, 사람 메시지(개입 모드).
- 기록 형식 (세팅 중 확인): 이어서 호출한 메시지는 서브에이전트 트랜스크립트에 `isMeta` user 레코드로 남고 "The coordinator sent a message while you were working:" 머리말이 붙습니다. 데스크톱 앱에서는 서브에이전트의 최종 보고가 `SubagentHandback` 도구 호출의 `message`로 전달됩니다. `collect.py`는 두 형식과 일반 텍스트 보고를 모두 처리합니다.
- 메시지 종류와 코딩 기준은 `research/config/message-codebook.md`에 정의합니다.

### 6.4 분석 관점

| 관점 | 질문 | 방법 |
|---|---|---|
| 구성 | 메인이 쓴 지시에 무엇이 들어 있는가? | 코드북의 구성 요소(목표, 맥락, 입력 참조, 제약, 완료 조건, 출력 형식 등) 유무를 메시지마다 표시 |
| 전달 방식 | 파일을 가리키는가, 내용을 붙여 넣는가? 길이와 토큰은? | 코딩 + 토큰 집계 |
| 중계 변형 | 보고가 메인을 거쳐 다음 에이전트에게 갈 때 무엇이 빠지고 더해지는가? | 보고와 그 보고를 근거로 쓴 다음 지시를 쌍으로 비교 (보존·누락·추가·재해석) |
| 원인 추적 | 루프가 길어진 경우 어느 메시지에서 오해가 시작됐는가? | 실패 루프를 거꾸로 따라가며 사례 분석 |
| 사람 vs LLM | 사람이 쓴 지시와 메인이 쓴 지시는 어떻게 다른가? | 개입 모드의 사람 메시지와 메인 메시지 비교 |
| 효율 | 어떤 지시가 적은 토큰과 적은 루프로 끝나는가? | 구성 요소와 결과(루프 횟수, 토큰)의 관계를 사례 중심으로 서술 |

코딩은 파이프라인 밖의 별도 LLM 세션이 1차로 하고, 사람이 무작위 20%를 검수합니다. 검수에서 불일치가 많으면 코드북을 고친 뒤 다시 코딩합니다.

### 6.5 인사이트 관리

- `docs/insights/`에 발견한 패턴을 **카드 한 장씩** 정리합니다 (`PI-001-<짧은-이름>.md`).
- 카드 항목: 관찰, 근거 메시지 링크(실행·메시지 번호), 해석, **사람이 프롬프트를 쓸 때의 시사점**, 확신도(사례 수).
- 효과가 좋았던 지시와 나빴던 지시를 원문 그대로 비교 예시로 모읍니다 (`docs/insights/examples/`).
- 카드는 실험이 진행되는 동안 계속 추가하고, 최종 보고서에서 묶어 정리합니다.

### 6.6 선택 실험: 소통 프로토콜 비교

본 실험(5절)이 끝난 뒤, 예산이 허락하면 F1에서 다음을 비교합니다.

| 조건 | L2 지시 프롬프트 |
|---|---|
| 자유 (본 실험과 같음) | 형식 없음 |
| 양식 | 6.4에서 효과가 좋았던 구성 요소를 묶은 지시 양식을 강제 |

토큰과 루프 횟수 차이로 "효율적인 프롬프트"를 직접 검증합니다. 반복은 조건별 2회입니다.

## 7. 레포 구조 (확정 2026-10-29)

원칙: **계약 역할을 하는 부분만 고정하고, 나머지는 메인 세션이 기능별 계획에서 결정합니다.**

- 고정하는 이유: 숨긴 평가 테스트를 모든 실행 결과에 똑같이 돌리고, 두 모드의 결과를 비교하고, 에이전트별 쓰기 영역을 제한하기 위해서입니다.
- 나머지를 자유롭게 두는 이유: 메인 세션이 코드 구조를 어떻게 설계하는지도 관찰 데이터이기 때문입니다.

표시: **[고정]** 세팅 단계에서 만들고 실험 중 계약을 바꾸지 않음 · **[자유]** 메인 세션과 에이전트가 결정 · **[연구]** 연구용, 실행 worktree에서는 제외

### 7.1 전체 구조

```
agent-pipeline-lab/
├── CLAUDE.md                        [고정] 모든 에이전트가 읽는 짧은 공통 규칙
├── pyproject.toml, uv.lock          [고정] uv 프로젝트 설정 (의존성 추가는 허용)
├── src/shortlink/
│   ├── __init__.py                  [고정]
│   ├── main.py                      [고정] create_app() — 앱 진입점
│   ├── config.py                    [고정] Settings — 환경 변수 기반 설정
│   ├── templates/, static/          [자유] 화면 템플릿과 CSS (위치는 고정)
│   └── (나머지)                      [자유] 예: api/, services/, db.py, schemas.py
├── tests/
│   ├── conftest.py                  [고정] 임시 DB와 테스트 클라이언트 픽스처
│   └── test_*.py                    [자유] test-writer 작성
```

### 7.2 서비스 코드 계약

고정하는 것은 **파일 위치, 이름, 시그니처, 환경 변수 이름**입니다. 함수 본문은 에이전트가 구현합니다.

| 파일 | 계약 |
|---|---|
| `src/shortlink/main.py` | `create_app(settings: Settings \| None = None) -> FastAPI`. 앱 생성 시 라우터 등록과 DB 스키마 준비까지 끝냄. `/static` 경로에 `src/shortlink/static/`을 연결. 템플릿은 `src/shortlink/templates/`. import만으로 DB 파일이 생기지 않도록 모듈 수준 `app`은 두지 않고 `uvicorn shortlink.main:create_app --factory`로 실행 |
| `src/shortlink/config.py` | `Settings`: `db_path`(환경 변수 `SHORTLINK_DB_PATH`), `base_url`(`SHORTLINK_BASE_URL`). F3에서 API 키 항목 추가 예정 |
| `tests/conftest.py` | `client` 픽스처: 임시 DB 경로로 `create_app(Settings(...))`을 만들어 `TestClient` 제공 |

- 고정 파일은 **확장만 허용**합니다. 항목 추가는 되지만 기존 이름의 변경과 삭제는 안 됩니다.
- 숨긴 평가 테스트는 `create_app`과 `Settings`만 import하고 **HTTP 요청으로만** 검증합니다. 그래서 자유 영역의 내부 구조와 상관없이 모든 실행 결과를 똑같이 채점할 수 있습니다.

### 7.4 실행 worktree 구성과 격리 (v1.19)

비교 실험의 각 실행은 별도 worktree에서 돌립니다. 에이전트가 연구 문서나 숨긴 평가 테스트, 다른 실행의 결과를 보면 행동이 달라지므로 세 겹으로 막고 잡습니다.

**1. 연구 이력이 없는 출발 커밋 (막기)**

`new_run.py`가 실행마다 에이전트용 파일만 담은 **부모 없는 커밋**을 만들고 그 위에서 실행 브랜치를 시작합니다. 실행 안에서 `git log`를 해도 이 출발 커밋 하나만 보입니다.

| 포함 | 제외 |
|---|---|
| `src/`, `tests/`, `.claude/`, `CLAUDE.md`, `pyproject.toml`, `uv.lock`, `.python-version`, `.gitignore`, `research/hooks/` | `docs/00-*`, `docs/01-*`, `docs/insights/`, `docs/journal/`, `README.md` |
| `docs/features/`의 **현재와 이전 기능 설계서**, `docs/plans/`, `docs/service.md`, `CHANGELOG.md` | `research/tools/`, `research/config/`, `research/eval/`, `research/runs/` |

- 다음 기능의 설계서는 넣지 않습니다. F2 실행은 호환성 요구 때문에 F1·F2 설계서를 봅니다.
- (v1.18까지는 main에서 갈라진 브랜치에 sparse checkout을 썼으나, worktree가 git 이력을 공유해 `git log`와 `git show main:...`으로 연구 커밋과 평가 테스트가 보였습니다.)

**2. hook으로 다른 기록 접근 차단 (막기)**

실험 worktree 안에서는 메인 세션과 서브에이전트 모두에 다음을 적용합니다(`research/hooks/runscope.py`). 연구 세션에는 적용하지 않습니다.

| hook | 막는 것 |
|---|---|
| `guard_bash.py` | 다른 브랜치나 전체 이력을 보는 git 명령(`--all`, `main`, `origin`, 다른 `run/` 브랜치, 태그, `git branch`, `git stash`, `git cat-file` 등), 연구 저장소 경로나 `research/eval`을 언급하는 명령, `git push` |
| `guard_read.py` | Read, Glob, Grep으로 프로젝트 폴더 밖이나 연구 저장소를 읽는 것 |
| `guard_write.py` | 프로젝트 폴더 밖에 쓰는 것, 역할별 쓰기 영역 밖에 쓰는 것 |

**3. 평가 테스트 표식 검사 (잡기)**

- 숨긴 평가 테스트 파일마다 고유한 표식(`EVAL-CANARY-...`)을 넣고, 테스트 함수 이름은 모두 `test_hidden_`으로 시작합니다.
- `collect.py`는 실행의 모든 트랜스크립트에서 (a) 평가 폴더를 언급한 도구 입력과 (b) 표식이나 `test_hidden_`이 들어간 도구 결과를 찾아 `eval-access.json`에 남깁니다.
- 하나라도 있으면 그 실행은 무효로 하고 다시 돌립니다. 1·2를 어떤 식으로 우회했든 내용이 에이전트에게 들어갔다면 잡힙니다.

남는 한계: Bash로 경로를 우회해서 만드는 경우(상위 폴더로 이동해 목록 보기 등)는 hook이 완벽히 막지 못하며, 3번 검사로 잡습니다. GitHub의 공개 저장소에서 가져오는 경우도 3번에 걸립니다.

- hook 로그는 worktree 안의 `research/logs/`(비공개)에 쌓이고, 실행이 끝나면 `collect.py`가 연구 저장소의 `research/runs/`로 모읍니다.

### 7.5 형상 관리 (확정 2026-10-29)

원칙: **main에는 기능마다 커밋 하나.** 중간 과정은 실행 브랜치에 체크포인트 커밋으로 남깁니다.

| 위치 | 커밋 | 누가 | 목적 |
|---|---|---|---|
| 실행 브랜치 `run/<기능>-<모드>-r<반복>` | 체크포인트 커밋 `wip(F1): <단계> <내용>` | 메인 세션 | 리뷰 2라운드부터 "직전 리뷰 체크포인트 이후 변경분"의 기준점, 단계별 코드 변화 기록(연구 데이터) |
| 실행 브랜치의 마지막 커밋 | 기능 커밋 `F1: <요약>` | doc-keeper | 서비스 문서, CHANGELOG, 계획, 결정 기록, 실행 보고서를 포함한 남은 변경 전체 |
| main | 기능마다 커밋 하나(실행 브랜치의 변경을 패치로 적용) + 다음 기능의 시작 태그 `baseline-F<n+1>` | 연구 세션 (`promote.py`) | 기능 단위 형상 관리 |

체크포인트 시점 (오케스트레이션 지침 `run-feature`):

| 시점 | 메시지 예 |
|---|---|
| 1단계 계획과 스켈레톤 후 | `wip(F1): 1 계획과 스켈레톤` |
| 2단계 구현과 테스트 작성 후 | `wip(F1): 2 구현과 테스트 작성` |
| 테스트 루프의 수정마다 | `wip(F1): 3 테스트 루프 2회차 수정` |
| 리뷰 라운드의 수정이 끝날 때마다 | `wip(F1): 4 리뷰 1라운드 수정` |
| 마지막 | `F1: 단축 URL 생성과 리다이렉트` (doc-keeper) |

- 커밋 명령은 `git add -A --sparse`를 씁니다. 실행 worktree는 sparse 상태라서, 영역 밖에 파일이 하나라도 생기면 `--sparse` 없이는 `git add`가 실패합니다(검증 중 확인).
- 실행 보고서는 doc-keeper보다 먼저 써서 기능 커밋 하나에 함께 담습니다.
- `collect.py --worktree`는 실행 브랜치의 커밋 목록을 `checkpoints.csv`로 남기고, 쓰기 영역 밖에서 바뀐 파일을 표시합니다.
- `promote.py F1 auto 1`은 선택한 실행의 변경(출발 커밋..실행 브랜치)을 main에 3-way 패치로 적용해 커밋 하나로 만들고 `baseline-F2` 태그를 붙입니다. 실행 브랜치가 main과 이력을 공유하지 않기 때문입니다. 쓰기 영역 밖 변경이 있으면 거절하고, 사람이 확인한 뒤 `--allow-outside`로 진행합니다. push는 하지 않습니다.
- 실행 세션은 브랜치를 바꾸거나 main을 건드리지 않고, push도 하지 않습니다(`guard_bash.py`).
