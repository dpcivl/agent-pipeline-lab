# F1 설계서 해석 결정 기록

auto 모드에서 메인 세션이 내린 해석입니다. 설계서(`docs/features/F1.md` v2)만으로 정해지지 않는 부분을 기록합니다.

## D-1 스킴 대소문자

- 설계서: "스킴이 `http` 또는 `https`가 아님"
- 결정: 스킴은 대소문자를 구분하지 않고 비교한다. `HTTPS://example.com`도 허용하고, 저장과 응답은 받은 그대로 한다.
- 이유: RFC 3986에서 스킴은 대소문자를 구분하지 않고, 브라우저도 같게 다룬다. 정규화 금지 규칙은 저장 값에만 적용한다.

## D-2 공백과 제어 문자가 든 URL

- 설계서: 거절 조건 4가지(필드 없음·문자열 아님·빈 값, 스킴, 호스트, 길이)만 나열하고 정규화를 금지한다.
- 결정: 공백 문자(스페이스, 탭, 줄바꿈 등 `str.isspace()`)나 제어 문자(U+0000~U+001F, U+007F)가 하나라도 있으면 422로 거절한다. 앞뒤 공백도 지우지 않고 거절한다.
- 이유: 이런 URL은 `Location` 헤더에 그대로 넣을 수 없어 리다이렉트가 깨지거나 헤더 주입 위험이 생긴다. 정규화(공백 제거)는 금지되어 있으므로 거절이 남은 선택이다. 파이썬 `urlsplit`이 앞쪽 공백을 조용히 무시해 `" https://..."`를 통과시키는 문제도 막는다.

## D-3 비ASCII 문자가 든 URL의 리다이렉트

- 설계서: "`Location: <원래 URL>`", "URL은 받은 그대로 저장하고 돌려줍니다."
- 결정: 저장과 API 응답은 받은 그대로 한다. 리다이렉트할 때 `Location` 헤더에서만 비ASCII 문자를 UTF-8 퍼센트 인코딩하고, ASCII 문자는 한 글자도 바꾸지 않는다. Starlette `RedirectResponse`의 기본 인용(`<`, `>`, `"` 등까지 인코딩)은 쓰지 않는다.
- 이유: HTTP 헤더는 ASCII(latin-1)만 담을 수 있어 비ASCII를 그대로 넣으면 서버 오류가 난다. 브라우저가 주소창 입력을 보내는 방식과 같아서 목적지는 같다. ASCII URL은 AC-10대로 글자 그대로 나간다.

## D-4 422 응답 본문

- 설계서: 상태 코드만 정한다.
- 결정: API는 `{"detail": "<한국어 오류 문구>"}`, 폼은 오류 문구를 담은 HTML. JSON 본문이 깨졌거나 객체가 아닐 때도 API는 422를 돌려준다.
- 이유: FastAPI 관례(`detail`)를 따르고 화면과 같은 문구를 써서 일관성을 지킨다.

## D-5 찾을 수 없음 응답 형식

- 설계서: AC-11은 404만, AC-21은 404 HTML 화면을 요구한다.
- 결정: 없는 코드의 `GET /{code}`는 클라이언트 종류와 상관없이 항상 404 HTML 화면을 돌려준다. 코드 형식(7자 영숫자)이 아닌 경로도 같은 404 화면이다.
- 이유: 두 수용 기준을 동시에 만족하는 가장 단순한 방식이다.

## D-6 created_at 정밀도

- 결정: 초 단위까지, `Z` 접미사 (`2026-10-29T01:23:45Z`). 설계서 예시 형식을 그대로 따른다.

## D-7 폼 입력칸 타입

- 결정: `type="text"`를 쓰고 `required`를 붙이지 않는다.
- 이유: `type="url"`이나 `required`를 쓰면 브라우저가 먼저 막아서 서버의 422 오류 화면(AC-19)이 사용자 흐름에서 보이지 않는다. 검증은 서버가 맡는다.

## D-8 파싱할 수 없는 URL (구현 중 결정, implementer)

- 결정: `urlsplit`이 `ValueError`를 내는 URL(예: `http://[abc`)은 "호스트 없음" 문구로 422 처리한다.
- 이유: 검증 중 예외가 나면 500이 된다. 파싱이 안 되면 호스트를 알 수 없으므로 호스트 문구가 가장 가깝다.

## D-9 JSON 본문 형식 오류 문구 (구현 중 결정, implementer)

- 결정: 본문이 JSON이 아니거나 객체가 아니면 422 `{"detail": "요청 본문은 {\"url\": ...} 형태의 JSON 객체여야 합니다."}`.
- 이유: D-4는 상태 코드만 정했고 문구가 없었다.

## D-10 짝 없는 서로게이트 문자 (리뷰 1라운드 R-1/S-1/Q-1 반영)

- 결정: URL에 서로게이트 문자(U+D800~U+DFFF)가 하나라도 있으면 422로 거절한다. 문구는 `URL에 쓸 수 없는 문자가 있습니다.`이고, 검사 위치는 D-2 공백·제어 문자 검사 바로 다음(스킴 검사 전)이다. API와 폼이 같은 `validate_url` 규칙을 쓴다.
- 이유: JSON 이스케이프(`"\ud800"`)로 들어온 짝 없는 서로게이트는 UTF-8로 저장할 수 없어 SQLite 저장 단계에서 500이 난다. "받은 그대로 저장"할 수 없는 값이므로 거절하는 것이 유일한 선택이다. 기존 D-2 문구는 이 경우를 설명하지 못해 새 문구를 둔다.
- 범위: C1 제어 문자, 양방향 제어 문자 같은 Cc/Cf 범주 전체를 거절하자는 제안(S-3)은 minor로 기록만 하고 이번에는 적용하지 않는다.
