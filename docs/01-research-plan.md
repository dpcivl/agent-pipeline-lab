# 연구 계획서 — 사람과 Claude 서브에이전트가 함께 일하는 개발 파이프라인

작성일: 2026-10-29
상태: P2 측정 완료, P3 파일럿 준비 전 (아래 "현재 상태" 참고)
상세 설계: [00-pipeline-design.md](00-pipeline-design.md)

---

## 1. 배경

Claude Code의 서브에이전트를 역할별로 나누면 구현, 테스트, 리뷰, 보안 점검 같은 개발 단계를 에이전트들이 나눠 맡을 수 있습니다. 그러나 다음은 잘 알려져 있지 않습니다.

- 에이전트끼리 실제로 어떤 프롬프트를 주고받는가
- 그 소통에 토큰이 얼마나 드는가
- 기능 하나를 끝까지 만드는 데 전체 비용이 얼마인가
- 사람이 개입하면 결과물과 비용이 어떻게 달라지는가
- 에이전트끼리의 소통에서 사람이 프롬프트를 더 잘 쓰는 데 쓸 수 있는 교훈은 무엇인가

이 연구는 작은 서비스를 실제로 이 파이프라인으로 만들면서 위 질문에 대한 측정값을 남기는 것이 목적입니다.

## 2. 목표

**최종 목표:** 사람의 개입을 최소화하고 에이전트끼리 프롬프트를 주고받으며 기능을 완성하는 개발 워크플로우를 만들고, 그 동작 방식과 비용을 측정해 공개합니다.

**핵심 관심사:** 에이전트끼리 주고받는 프롬프트의 **내용과 소통 과정**을 들여다보고, 사람이 프롬프트를 쓸 때 활용할 수 있는 효율적인 프롬프팅 패턴을 찾는 것입니다.

**적용 관점:** 이 파이프라인을 **실제 웹·앱 개발 프로젝트**에 쓸 수 있는지 판단할 근거를 얻는 것입니다. 그래서 대상 서비스는 API와 웹 화면을 함께 가진 웹 서비스이고, 사람이 화면 목업을 보고 승인하는 단계를 포함합니다.

### 연구 질문

| # | 질문 | 답을 얻는 방법 |
|---|---|---|
| Q1 | 메인 세션과 서브에이전트 사이에 오가는 raw 프롬프트는 어떤 형식인가? | 트랜스크립트에서 지시 프롬프트와 보고 원문을 추출해 공개 |
| Q2 | 에이전트 간 소통에 쓰이는 토큰은 얼마이고, 전체 대비 비중은? | 통신 엣지별 토큰 집계 |
| Q3 | 기능 하나를 끝까지 구현하는 데 드는 총 토큰·비용·시간과 단계별 분포는? | 실행별 usage 집계 |
| Q4 | 이 파이프라인이 웹 화면이 있는 서비스에서도 실제로 동작하는가? 목업 → 승인 → 구현 흐름이 쓸모 있는가? | 파일럿 실행으로 끝까지 완주하는지, 구현된 화면이 목업을 따르는지 확인 |
| Q5 | 사람이 개입할 때와 하지 않을 때 결과물 품질과 토큰 사용량은 어떻게 다른가? | 자율 모드와 개입 모드 비교 실험 |
| Q6 | 메인이 쓰는 지시 프롬프트는 어떤 내용과 구조인가? 보고가 메인을 거쳐 전달될 때 무엇이 빠지고 더해지는가? | 메시지 단위 수집, 코드북 기반 코딩, 보고와 다음 지시의 쌍 비교 |
| Q7 | 사람이 프롬프트를 쓸 때 활용할 수 있는 효율적인 프롬프팅 패턴은 무엇인가? | 구성 요소와 결과(루프·토큰)의 관계, 사람 vs LLM 지시 비교, 인사이트 카드 |

### 범위 밖

- 여러 LLM 제공사 비교
- 대규모 코드베이스나 실서비스 운영
- 통계적으로 일반화 가능한 결론 (반복 횟수가 적은 사례 연구입니다)

## 3. 연구 대상

**ShortLink — URL 단축 웹 서비스** (Python 3.12, uv, FastAPI, Jinja2 서버 렌더링, SQLite, pytest). JSON API와 웹 화면을 함께 제공합니다.

| 기능 | 내용 | 측정 포인트 |
|---|---|---|
| F1 | 단축 URL 생성, 리다이렉트, 기본 화면 4개 | 처음부터 만드는 기준선, 목업 확인 단계 |
| F2 | 클릭 통계, 커스텀 별칭, 통계 화면 | 기존 코드와 화면을 수정하는 비용 |
| F3 | API 키 인증, 만료, 삭제, 관리 화면 | 보안 지적과 수정 루프 비용 |

도메인이 잘 알려져 있어 에이전트가 도메인 이해에 쓰는 토큰이 적습니다. 그래서 파이프라인 자체의 오버헤드를 분리해서 보기 좋습니다.

## 4. 방법

### 4.1 파이프라인

```
설계서(사람) → 계획·인터페이스 스켈레톤(메인) → 승인(사람)
→ [구현 ∥ 테스트 작성]
→ 테스트 루프 (tester 판정 → 원인별로 구현/테스트 작성 에이전트가 수정, 최대 5회)
→ 리뷰 루프 ([리뷰 ∥ QA ∥ 보안] → 구현 에이전트 수정 → 재테스트, 최대 5라운드)
→ 문서·커밋 → 보고서(메인)
```

| 역할 | 모델 |
|---|---|
| 메인 세션, reviewer, security | Opus 5.5 |
| implementer, test-writer, tester, qa | Sonnet 5.5 |
| doc-keeper | Haiku 5.5 |

서브에이전트끼리는 직접 대화하지 않습니다. 모든 소통은 메인 세션을 거치는 프롬프트와 보고, 그리고 공유 파일입니다.

### 4.2 측정

| 대상 | 방법 |
|---|---|
| raw 프롬프트 | Claude Code 트랜스크립트(JSONL)에서 Agent 호출과 서브에이전트 기록을 연결해 추출. hook으로 실시간 보조 기록 |
| 토큰 | 모든 API 호출의 usage(input, output, cache write, cache read, thinking)를 에이전트별·단계별·통신 엣지별로 집계 |
| 비용 | 모델별 단가표로 API 환산 비용 계산 |
| 품질 | 레포 밖에 숨겨 둔 평가 테스트 통과율, 정적 분석, 블라인드 비교 평가(Fable 5.1) |
| 사람 비용 | 개입 횟수, 소요 시간, 메시지 |

각 에이전트의 시스템 프롬프트는 트랜스크립트에 기록되므로 크기를 집계합니다. 원문에는 Claude Code 내장 프롬프트와 세션 정보가 섞여 있어 공개하지 않습니다. 역할별로 빈 작업을 한 번씩 실행해 고정 오버헤드 토큰도 따로 측정합니다.

### 4.3 에이전트 간 소통 분석

서브에이전트끼리는 직접 대화하지 않고 모든 메시지가 메인 세션을 거칩니다. 분석 대상 프롬프트는 세 층입니다.

| 층 | 누가 쓰나 | 방침 |
|---|---|---|
| 역할 정의 | 우리 (사람) | 고정 |
| 지시 프롬프트 | 메인 세션 (LLM) | **자유** — LLM이 원래 어떻게 지시를 쓰는지 관찰하기 위해 형식을 정하지 않음 |
| 보고 | 서브에이전트 (LLM) | **형식 고정** — 메인이 다음 단계를 판단할 수 있도록 |

- **수집:** 모든 메시지를 메시지 한 개당 파일 하나로 저장하고, 실행마다 메시지 흐름 다이어그램을 자동 생성합니다.
- **코딩:** 코드북(`research/config/message-codebook.md`) 기준으로 메시지의 종류와 구성 요소를 표시합니다. 별도 LLM이 1차로 하고 사람이 20%를 검수합니다.
- **분석:** 지시의 구성, 파일 참조와 내용 붙여넣기의 차이, 메인을 거치며 생기는 정보 변형, 루프가 길어진 원인, 사람과 LLM의 지시 차이를 봅니다.
- **인사이트:** 발견한 패턴을 `docs/insights/`에 카드로 정리하고 좋은/나쁜 예시를 함께 모읍니다.
- **선택 실험:** 본 실험 후 F1에서 자유 지시와 양식 지시를 비교합니다.

상세: [00-pipeline-design.md 6절](00-pipeline-design.md#6-에이전트-간-소통-분석)

### 4.4 비교 실험

| 조건 | 내용 |
|---|---|
| 모드 | 자율(사람 개입 0회) vs 개입(정해진 4개 시점에 사람 개입) |
| 반복 | 기능 3개 × 모드 2개 × 2회 = 12회 |
| 통제 | 같은 git 태그에서 별도 worktree, 같은 설계서·모델·에이전트 정의, 설정 파일 해시 기록 |
| 순서 | 자율 모드를 먼저 실행하고 결과는 개입 모드가 끝날 때까지 보지 않음 |

파일럿(P3)에서 파이프라인을 고쳐야 하면 고친 뒤에 비교 실험을 시작합니다. 비교 실험 도중에는 파이프라인을 바꾸지 않습니다.

## 6. 산출물

- 설계 문서와 연구 계획서 (`docs/`)
- 에이전트 정의, hook, 측정 스크립트 (재현 가능하도록 공개)
- 실행별 에이전트 간 메시지 원문과 흐름 다이어그램 (비식별화 후 공개)
- 메시지 코드북과 코딩 데이터
- 프롬프트 패턴 인사이트 카드와 좋은/나쁜 예시 (`docs/insights/`)
- 실행별 토큰·비용·품질 데이터 (CSV, JSON)
- 최종 보고서 (`research/REPORT.md`)
- 연구 일지 (`docs/journal/`)

- 커밋 전에 개인 정보 패턴을 검사하는 단계를 둡니다.

## 8. 위험과 한계

| 위험 | 대응 |
|---|---|
| LLM 결과가 실행마다 다름 | 2회 반복, 평균과 범위를 함께 보고, 사례 연구로 표기 |
| 반복 횟수가 적어 통계적 결론 불가 | 차이가 실행 간 편차보다 클 때만 경향으로 서술 |
| Claude Code 버전이 바뀌면 동작과 트랜스크립트 형식이 바뀔 수 있음 | 실행마다 버전 기록, 실험 기간에는 업데이트를 미룸 |
| 시스템 프롬프트 원문은 공개할 수 없음 | 크기만 공개, 고정 오버헤드를 따로 측정 |
| 구독 요금제 사용 시 실제 청구액과 다름 | 모든 비용은 API 환산 비용으로 표기 |
| 에이전트가 숨긴 평가 테스트를 읽을 수 있음 | 레포 밖에 보관, 트랜스크립트에서 접근 흔적을 검사해 무효 처리 |
| 서비스 범위 변경(API만 → 웹 화면 포함) 후 P2 고정 오버헤드 값이 조금 달라짐 | 에이전트 정의가 수백 글자 늘어남. 필요하면 P2를 다시 측정(비용 약 $0.85) |
| 화면 검증이 HTML 응답 수준에 머묾 | 브라우저 자동화(Playwright)는 브라우저 다운로드가 필요해 보류. 목업과의 시각적 비교는 사람(H1)과 블라인드 평가에서 다룸 |
| 기능 설계서를 사람이 아니라 연구 세션(Claude)이 작성 | 서비스를 추천받아 진행하므로 연구자가 직접 설계하기 어려움. Claude가 초안을 쓰고 연구자가 검토·수정한 뒤 확정. 보고서에 "설계서 작성 주체"를 조건으로 명시하고, 사람이 쓴 설계서였다면 달라졌을 수 있는 점(모호함의 양, 표현 방식)을 한계로 적음 |
| 에이전트가 Bash로 파일을 써서 쓰기 영역 hook을 우회 | 실행 후 `git diff`로 사후 확인, 권한 모드 결정 시 고려 |
| 루프가 길어져 비용이 커짐 | 루프 한도(5회) 유지, 실행별 비용을 즉시 집계해 이상치 확인 |
