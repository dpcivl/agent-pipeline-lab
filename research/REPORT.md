# 정리 보고서: 사람과 Claude 서브에이전트가 함께 일하는 개발 파이프라인

작성일: 2026-10-30. 실험은 F2 실행까지 하고 중단했습니다(F3은 실행하지 않음).

이 보고서는 다음 세 질문에 답합니다.

1. 에이전트끼리 어떤 프롬프트를 주고받았는가?
2. 구현과 검증은 어떤 식으로 진행되었는가?
3. 토큰과 비용은 얼마나 들었는가?

근거 데이터는 유효한 실행 9개입니다. F1 파일럿 1개, F1 비교 4개, F2 비교 4개이며 모두 `research/runs/` 아래에 있습니다.

## 요약

- **소통 형식.** 메인 세션은 서브에이전트에게 300~800토큰의 짧은 지시를 보냈습니다. 지시는 "할 일, 읽을 문서, 요점, 금지 사항, 보고 형식" 구조였습니다. 서브에이전트는 정해진 보고 형식으로 200~3,000토큰을 돌려보냈습니다. 보고가 지시보다 3~4배 깁니다.
- **소통 토큰은 아주 작습니다.** 에이전트끼리 주고받은 메시지는 기능 하나에 1.2만~2.4만 토큰입니다. 이는 전체 처리 토큰(650만~1,330만)의 **0.14~0.22%**입니다. 토큰 대부분은 각 에이전트가 파일과 대화 맥락을 반복해서 읽는 데(캐시 읽기) 쓰였습니다.
- **비용.** 기능 하나(API + 웹 화면 + 테스트 + 문서)에 API 환산 **$4.78~8.58**, **650만~1,330만 토큰**, **15~46분**이 들었습니다. 비용의 약 절반(44~55%)은 메인 세션(Opus)에서 나왔습니다.
- **비용을 가른 것은 리뷰 라운드 수입니다.** 1라운드에서 major 지적이 나와 수정 → 재테스트 → 2라운드 리뷰를 거치면 $1.5~3과 몇 분에서 25분이 더 들었습니다.
- **검증.** 숨긴 평가 테스트(F1 107개, F2 152개)를 9개 실행이 모두 100% 통과했습니다. 파이프라인 안의 리뷰 단계는 평가 테스트가 다루지 않는 결함을 실제로 찾았습니다. F1에서는 짝 없는 서로게이트 문자로 인한 500, F2에서는 동시 시작 시 마이그레이션 실패였습니다.
- **비교 실험 중단.** 자율(auto)과 개입(human)을 비교하려 했습니다. 그러나 개입 실행에서 사람이 메인 세션의 권장안을 그대로 골랐기 때문에, 사람의 검토가 들어간 비교가 되지 못했습니다. 그래서 Q5(사람 개입의 효과)에는 답하지 않고 실험을 정리합니다. 이 현상 자체는 중요한 관찰로 남깁니다(6절).

## 2. 에이전트끼리 주고받은 프롬프트

모든 메시지 원문은 실행 폴더의 `messages/`에 한 파일씩 있습니다(예: `research/runs/F1/auto/r2/messages/`). `flow.md`는 메시지 흐름을 시퀀스 다이어그램으로 보여 줍니다.

### 2.1 메시지 크기 (9개 실행 평균, 추정 토큰)

| 역할 | 지시 (메인 → 역할) | 보고 (역할 → 메인) |
|---|---|---|
| implementer | 631 | 1,124 |
| test-writer | 618 | 1,726 |
| tester | 228 | 182 |
| reviewer | 281 | 1,898 |
| qa | 328 | 1,387 |
| security | 276 | 2,390 |
| doc-keeper | 438 | 455 |

- 일을 만드는 역할(implementer, test-writer)은 지시가 깁니다.
- 판단하는 역할(reviewer, security, qa)은 지시가 짧고 보고가 깁니다. 지적마다 위치, 문제, 근거, 수정 제안을 쓰기 때문입니다.
- tester는 지시와 보고가 모두 가장 짧습니다. "PASS, 통과 89 / 실패 0"이면 끝납니다.

### 2.2 지시 프롬프트의 구조

메인이 쓴 지시는 실행과 역할이 달라도 거의 같은 뼈대였습니다. 다음은 implementer 첫 지시를 줄인 것입니다(F1 auto r2, 원문 623토큰).

```text
F1(단축 URL 생성과 리다이렉트)을 구현해 줘.                  ← 할 일 한 줄

읽을 문서:                                                   ← 내용을 붙이지 않고 경로만 줌
- 설계서: docs/features/F1.md (수용 기준 AC-1~AC-23)
- 구현 계획: docs/plans/F1-plan.md (...)
- 해석 결정: docs/plans/F1-decisions.md (D-1~D-7, 특히 D-2 ...)
- 화면 목업: docs/plans/mockups/F1-home.html, ...

스켈레톤이 이미 있다: ... 스텁을 채우고 다음을 새로 만든다:   ← 현재 상태와 산출물 목록
- src/shortlink/templates/: base.html, home.html, ...

요점:                                                         ← 판단 기준과 금지 사항
- 템플릿은 목업의 마크업 구조, 클래스 이름, 문구를 그대로 따른다.
- Jinja2 자동 이스케이프를 유지하고 |safe, Markup은 쓰지 않는다.
- 테스트는 test-writer가 동시에 쓰고 있다. tests/는 건드리지 마라.
- 끝나기 전에 uv run ruff check src, uv run ruff format src를 실행한다.

보고는 네 정의의 보고 형식으로.                              ← 형식은 역할 정의에 맡김
```

관찰한 특징은 다음과 같습니다.

- **문서는 경로로만 전달했습니다.** 설계서나 계획 내용을 지시에 붙이지 않고, 서브에이전트가 직접 읽게 했습니다. 그래서 지시가 짧게 유지되었습니다.
- **병렬 작업자 사이의 경계를 명시했습니다.** "tests/는 test-writer가 쓰고 있으니 건드리지 마라"처럼 동시에 일하는 쪽의 영역을 알려 줍니다.
- **리뷰 지시에는 검토 범위를 커밋 해시로 줬습니다.** 예: `git diff e8f75ad..166f2b6`. 2라운드에서는 "R-1이 해결됐는지, 이번 diff에 새 문제가 있는지 두 가지만 봐 줘"처럼 범위를 좁혔습니다.
- **앞 단계의 질문을 다음 단계로 넘겼습니다.** implementer가 보고 끝에 "서로게이트 문자는 저장할 때 500이 날 수 있다"는 질문을 남겼습니다. 메인은 이를 reviewer 지시에 "이것도 판단에 포함해 줘"로 넘겼고, reviewer가 실제로 재현해 major로 판정했습니다.
- **수정 지시에는 메인의 결정이 들어갑니다.** 세 에이전트의 지적을 하나로 묶었습니다. 그 위에 거절 규칙, 오류 문구, 검사 위치까지 정한 결정(D-10)을 담아 implementer에 보냈습니다. 반영하지 않을 minor도 명시했습니다("S-3이나 그 밖의 minor 지적은 이번에 반영하지 않는다").
- **SendMessage로 다시 부를 때는 Claude Code가 문구를 붙였습니다.** 지시 끝에 "Address this before completing your current task."가 자동으로 붙었습니다.

### 2.3 보고 형식

보고 형식은 역할 정의(`.claude/agents/*.md`)에 고정해 두었습니다. 그래서 9개 실행 모두 첫 줄이 같은 꼴입니다.

| 역할 | 첫 줄 | 본문 |
|---|---|---|
| implementer, test-writer | `## 결과: 완료` | 변경 파일, 구현한 수용 기준, 계획에 없던 판단, 남은 문제와 질문 |
| tester | `## 결과: PASS` | 통과/실패 수, 실패별 분류, 린트 결과, 파일을 바꾸지 않았다는 확인 |
| reviewer, qa, security | `## 결과: 지적 4건 (blocker 0, major 1, minor 3)` | 지적마다 번호(R-/Q-/S-), 심각도, 위치, 문제, 근거, 수정 제안. 2라운드부터는 "이전 지적 확인" |
| doc-keeper | `## 결과: 완료` | 갱신한 문서, 커밋 해시, 확인 필요 사항 |

- **"계획에 없던 판단"과 "남은 문제와 질문" 칸이 가장 쓸모 있었습니다.** 서로게이트 결함도 이 칸에서 처음 나왔습니다.
- **에이전트는 지시를 그대로 따르지 않고 근거를 대며 되묻기도 했습니다.** doc-keeper는 커밋 서명을 지시받은 Opus가 아니라 실제 실행 모델인 Haiku로 적었습니다. 그리고 "이력 수정 금지 조건 때문에 직접 고치지 않았다"고 보고했습니다.

## 3. 검증은 어떻게 했나

검증은 네 겹이었습니다. 세 겹은 파이프라인 안이고, 한 겹은 파이프라인 밖입니다.

| 층 | 누가 | 방법 | 실제로 잡은 것 |
|---|---|---|---|
| 자체 테스트 | test-writer가 쓰고 tester가 실행 | 설계서의 AC마다 pytest. 실행은 tester만, 수정은 작성자만 | F1·F2 모든 실행이 1회차에 통과 (실행당 89~452개) |
| 코드 리뷰 | reviewer (Opus) | 체크포인트 diff를 읽고 설계서·계획·목업과 대조. 파일 수정과 서버 실행은 하지 않음 | 서로게이트 500(F1), 원자적이지 않은 마이그레이션(F2), 스텁 시절 docstring, 약한 단언 |
| 블랙박스 QA | qa (Sonnet) | 임시 DB로 서버를 실제로 띄우고 HTTP 요청으로 AC 전부를 확인. 화면 HTML을 목업과 비교. 재시작 뒤 데이터 유지 확인 | 비문자열 입력의 422 본문 형식, 목업 문구 불일치 |
| 보안 | security (Opus) | 코드 점검과 저장소 밖 스크립트로 재현 | 마이그레이션 경쟁을 4개 프로세스로 재현(120번 중 90번 실패), 리다이렉트의 쓰기 잠금 경합, 클릭 부풀리기 |
| 숨긴 평가 테스트 | 연구 인프라 (파이프라인 밖) | 에이전트가 볼 수 없는 위치의 테스트를 실행 후 채점. 읽기 hook과 canary 문자열로 접근 여부 확인 | 9개 실행 모두 100% 통과. 접근 흔적 0건 |

관찰한 점은 다음과 같습니다.

- **같은 결함을 여러 에이전트가 독립적으로 찾았습니다.** F1 서로게이트 결함은 reviewer, qa, security가 모두 지적했습니다. F2 마이그레이션 경쟁은 네 실행 모두에서 reviewer나 security가 찾았습니다.
- **심각도 판정이 결과를 정했습니다.** F2 마이그레이션 경쟁은 실제로 재현되는 시작 실패인데도 모든 실행에서 minor로 판정됐습니다. 자율 모드 규칙은 minor를 고치지 않으므로 이 결함은 남았습니다. 고친 것은 메인이 "major로 올려 고치자"고 권하고 사람이 따른 F2 human r1뿐입니다.
- **숨긴 평가 테스트는 천장 효과를 보였습니다.** 설계서 수용 기준만 확인하는 테스트로는 실행 간 품질 차이가 드러나지 않았습니다. 리뷰 단계가 찾은 결함(동시 시작, 잠금 경합)은 평가 테스트 범위 밖이었습니다.
- **역할 분리가 지켜졌습니다.** tester는 파일을 바꾸지 않았고, 매번 `git status`로 이를 확인해 보고했습니다. 쓰기 영역 밖 변경은 9개 실행 모두 0건이었습니다.

- 전체 토큰 = 입력 + 캐시 쓰기 + 캐시 읽기 + 출력입니다.
- 소통 토큰은 에이전트 간 메시지(지시 + 보고)의 글자 수 기반 추정치입니다.
- 시간에는 사람의 응답 대기가 들어 있습니다(F1 human r1 41분, F2 human r1 5분).

### 4.2 토큰은 어디에 쓰였나

- **약 92%가 캐시 읽기입니다.** 에이전트가 도구를 한 번 부를 때마다 그때까지의 대화 맥락 전체(시스템 프롬프트, 읽은 파일, 이전 도구 결과)를 다시 모델에 넣습니다. 이 반복 입력은 캐시에서 싸게 읽히지만, 토큰 수로는 압도적입니다.
- **출력 토큰은 실행당 14만~20만입니다.** 코드, 테스트, 문서, 보고, 목업 HTML을 모두 합친 양입니다.
- **소통 메시지 자체는 0.2% 안팎입니다.** "에이전트끼리 대화하느라 토큰을 많이 쓴다"는 우려는 이 구조에서는 해당하지 않았습니다. 비용은 각 에이전트가 맥락을 다시 쌓는 데서 나옵니다.

### 4.3 역할별 평균 (9개 실행)

| 역할 | 모델 | 호출 수 | 토큰 | 비용 | 비용 비중 |
|---|---|---|---|---|---|
| 메인 세션 | Opus 5.5 | 39.8 | 5.58M | $3.06 | 49% |
| reviewer | Opus 5.5 | 13.7 | 0.73M | $0.96 | 15% |
| security | Opus 5.5 | 10.8 | 0.40M | $0.76 | 12% |
| test-writer | Sonnet 5.5 | 19.9 | 1.22M | $0.75 | 12% |
| implementer | Sonnet 5.5 | 14.8 | 0.63M | $0.41 | 7% |
| qa | Sonnet 5.5 | 13.0 | 0.42M | $0.27 | 4% |
| tester | Sonnet 5.5 | 3.8 | 0.04M | $0.05 | 1% |
| doc-keeper | Haiku 5.5 | 7.7 | 0.29M | $0.01 | 0.2% |

- **메인 세션이 비용의 절반입니다.** 메인의 기본 맥락이 약 7만 토큰으로 서브에이전트(약 8천)의 9배입니다. 또 서브에이전트 보고를 받을 때마다 이 맥락 전체를 다시 읽습니다.
- **메인 비용의 절반 가까이는 계획 단계입니다.** 메인 비용 가운데 계획, 스켈레톤, 목업 작성(첫 서브에이전트 호출 전)에 $1.3~1.9가 들었습니다. 나머지 $1.0~2.2는 조율입니다.
- **역할의 모델이 비용을 크게 바꿉니다.** test-writer는 토큰을 reviewer보다 많이 쓰지만 Sonnet이라 더 쌉니다. doc-keeper(Haiku)는 사실상 무료입니다.

### 4.4 고정 비용 (P2 측정)

- 서브에이전트를 한 번 부르는 데 일이 없어도 약 **7,700~8,300토큰**이 듭니다. 내장 지침, 도구 설명, 역할 정의를 합한 양이며, 역할 정의 자체는 약 2,000자입니다.
- 같은 역할을 다시 부르면 이 부분을 캐시에서 읽어 비용이 90~94% 줄어듭니다.
- 결과: `research/runs/P2/results.md`

## 5. 웹 개발에 적용할 수 있는가 (Q4)

적용할 수 있다고 봅니다.

- **9개 실행이 모두 끝까지 완주했습니다.** API, 서버 렌더링 화면 4~7장, CSS와 JS, 테스트, 문서를 기능 하나당 15~20분(사람 대기 제외), $5~9에 만들었습니다.
- **목업이 화면 구현의 기준으로 작동했습니다.** 메인이 HTML 목업을 먼저 만들면 implementer는 그 마크업과 문구를 템플릿으로 옮겼고, reviewer와 qa는 실제 HTML을 목업과 대조했습니다. 연구자도 목업을 브라우저로 열어 확인할 수 있었습니다.
- **한계도 있습니다.** 화면의 시각적 품질(배치, 색, 반응형)은 사람이 브라우저로 확인한 것 말고는 자동 검증이 없었습니다. qa는 HTML 문구와 구조만 확인합니다.

## 6. 비교 실험을 중단한 이유와 관찰

### 6.1 중단 이유

- 개입 모드는 사람이 네 시점(H1 계획 승인, H2 모호함, H3 지적 우선순위, H4 커밋 전 확인)에서 판단하도록 설계했습니다.
- 실제로는 연구자가 매번 메인의 권장안을 그대로 골랐습니다. 트랜스크립트로도 확인됩니다.
  - F2 human r1, H3: 메인이 "M-1(마이그레이션 경쟁)은 실제로 재현됐고 수정 비용이 작아서, R-1과 함께 major로 올려 이번에 고치는 방안을 권합니다"라고 제시했고, 연구자가 "M-1, R-1만 수정"으로 답했습니다.
  - F2 human r2, H3: 메인이 "절차상 minor는 기록만 하므로 이대로면 리뷰 루프를 끝냅니다"를 기본안으로 제시했고, 연구자가 "기록만, 다음 단계"로 답했습니다.
- 따라서 auto와 human의 차이는 "사람의 검토 유무"가 아닙니다. "메인이 규칙을 넘는 권장을 할 기회가 있었는지"의 차이에 가깝습니다. 사람 개입의 효과(Q5)를 재는 실험으로는 의미가 없다고 판단해 중단했습니다.

### 6.2 이 현상에서 얻은 것

- **권장안을 붙여 묻는 확인 절차는 승인 도장이 되기 쉽습니다.** 메인이 정리와 권장을 잘할수록, 사람은 검토하지 않고 고르게 됩니다. 사람의 검토를 실제로 받으려면 확인 절차를 다르게 설계해야 합니다. 예를 들면 다음과 같습니다.
  - 권장안 없이 선택지만 제시하기
  - 사람이 직접 서버를 띄워 확인한 결과를 적어야 다음으로 넘어가게 하기
  - 사람이 볼 항목을 미리 정해 두기
- **자율 모드 규칙이 메인 자신의 판단보다 보수적이었습니다.** human r1에서 메인은 재현된 결함을 고치자고 권했습니다. 반면 자율 모드에서는 "minor는 고치지 않는다"는 규칙 때문에 같은 판단을 하지 못했습니다. 그래서 자율 모드의 처리 규칙을 다음처럼 고치면 품질이 오를 가능성이 있습니다.
  - "재현된 실패는 major 이상"
  - "여러 에이전트가 같은 문제를 지적하면 수정"
  - "수정 비용이 작은 minor는 메인 판단으로 수정"

## 7. 사람이 프롬프트를 쓸 때 참고할 점 (Q7)

메인 세션이 쓴 지시에서 효과가 보인 패턴입니다.

1. **문서 내용 대신 경로와 읽을 부분을 준다.** "docs/plans/F1-plan.md, 특히 2, 3, 5절"처럼 줍니다. 지시가 짧아지고, 받는 쪽이 원문을 직접 확인합니다.
2. **결정은 지시 안에서 끝낸다.** 수정 지시에 "거절, 422, 문구는 정확히 '...', 검사 위치는 D-2 다음"까지 정해 주면 수정이 한 번에 끝났고, 다음 라운드에서 같은 지적이 다시 나오지 않았습니다.
3. **하지 않을 일도 적는다.** "tests/는 건드리지 마라", "minor는 이번에 반영하지 않는다"처럼 범위를 닫으면 병렬 작업이 충돌하지 않았습니다.
4. **검토 범위를 기계적으로 지정한다.** 커밋 해시 범위(`git diff A..B`)와 볼 항목을 주면 2라운드 리뷰가 짧고 좁게 끝났습니다(F1 auto r2는 세 역할 모두 1분 안팎, 보고 약 830토큰).
5. **보고 형식을 미리 고정한다.** 특히 "계획에 없던 판단"과 "남은 문제와 질문" 칸을 둡니다. 숨은 결함이 이 칸에서 올라왔습니다.
6. **심각도 기준을 구체적으로 준다.** 기준이 모호하면 실제 결함도 minor로 내려가고, 처리 규칙에 따라 버려집니다.
